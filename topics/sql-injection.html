01　概念介紹

SQL Injection（SQL 注入，簡稱 SQLi） 是一種發生在應用程式與資料庫交互時的安全弱點。問題通常出在開發者把使用者提供的資料直接拼接進 SQL 指令，使「原本應該只是資料」的內容有機會改變查詢的結構。

SQL Injection 屬於 OWASP Top 10:2025 的 A05:2025 — Injection 類別。影響可能包括非預期的資料查詢、資料修改或其他未授權操作，具體影響取決於系統與資料庫帳號權限。

本文範圍以下以虛構的會員查詢功能說明風險，重點在於防禦觀念與安全寫法，不涉及真實系統測試。

02　核心知識

問題根源：指令和資料沒有分開

應用程式會使用 SQL（Structured Query Language，結構化查詢語言）與資料庫溝通。當程式把外部字串直接串接成 SQL 指令時，資料庫無法可靠分辨哪些部分是程式想執行的查詢結構、哪些部分只是使用者輸入的資料。

不安全的程式設計模式（示意）直接把使用者輸入組合成 SQL 字串，會使查詢結構受到非預期輸入影響。
// 示意：請避免這種字串拼接方式
const query = "SELECT * FROM members WHERE name = '" + userName + "'";

核心修正方法：Parameterized Query

參數化查詢（Parameterized Query） 會先定義固定的 SQL 結構，再把使用者輸入的值透過資料庫驅動程式綁定進去，避免它被視為 SQL 語法的一部分。

03　實際案例

安全寫法：Python + SQLite

以下範例是 Python 標準程式庫 sqlite3 的概念示範。問號 ? 是參數位置，(user_name,) 表示要傳入的參數值。

import sqlite3

connection = sqlite3.connect("example.db")
cursor = connection.cursor()

user_name = "alice"  # 假設來自表單的輸入值
cursor.execute(
    "SELECT id FROM members WHERE name = ?",
    (user_name,)
)
rows = cursor.fetchall()
connection.close()

這個示範假設資料庫已存在 members 表格，並非整套可直接執行的網站。重點是使用參數綁定，而不是手動替每個字元加上跳脫符號。

參數化 ≠ 授權驗證即使 SQL 本身安全，應用程式仍需要另外檢查「這位使用者是否有權限讀取這筆資料」。

04　防禦與建議

  • 優先使用參數化查詢：避免直接串接不可信任輸入與 SQL 語句。
  • 限制動態識別字：資料表名稱、欄位名稱等不能當成一般資料值綁定，應由程式使用固定的允許清單（allow-list）選擇。
  • 落實最小權限：資料庫帳號只提供業務必要的權限，降低漏洞發生後的影響。
  • 輸入驗證是輔助：檢查格式、長度可以改善資料品質，但不能取代參數化查詢。
  • 定期進行程式碼審查：關注 ORM、儲存程序和動態查詢中是否有字串拼接。

手動跳脫輸入通常容易出錯，不應當成主要防禦措施。

05　重點整理

  • SQL Injection 的根本問題，是把不可信資料當成 SQL 結構的一部分。
  • 參數化查詢是處理動態資料值的主要防禦方式。
  • 對資料庫物件名稱等動態結構要使用固定允許清單。
  • 仍須落實授權檢查、最小權限及測試，才能形成多層防護。
